## Review follow-up: unconfirmed submits and idempotency

Correction: the "was not sent" wording I wrote earlier overstated what the client knows. A failed request can still have created the report. Codex's wording change ("We could not confirm your report was received...") is correct and kept.

- Web now sends an `Idempotency-Key` header (`web/src/api/client.ts` gained a `headers` option). The report form keeps one key per unchanged submission and creates a new key when the content changes. The key is cleared after success. The API contract (`api/src/services/reportService.js`) returns the stored report for a repeated key and returns 409 while a key is still in progress.
- Unit tests: unchanged retries after failures reuse one key. A changed report after a failure gets a new key (`ReportForm.test.tsx`, 2 tests).
- Browser, mocked response loss: the first POST reached the emulator (route.fetch), then the connection was aborted. The retry sent the same key and landed on one report. Two scenarios each produced exactly one emulator report.
- Still open: the API does not compare the key with the body, so a reused key with changed content returns the old report. The web avoids this by fingerprinting content. A keyed request for an accepted report after a page reload is not covered.
- Unsaved-entry protection is `beforeunload` only (reload or tab close). In-app navigation is not guarded. The app uses `BrowserRouter`, so React Router's `useBlocker` is not available without moving to a data router. **Decision needed:** accept the current behaviour, or move to a data router for an in-app warning.
- Developer comment in `ReportForm.tsx` mentions the retention policy. It is not product copy. Persistent drafts are not implemented.
