# Whole-product visual reset

For Airen · October 17, 2026. This is a correction to the design acceptance bar, not a cancellation of existing functional repairs or the whole-product ledger.

## Why the current result is rejected

Airen still considers the website sloppy, especially the landing. Earlier reviews confirmed individual improvements and functional checks; they did not establish that the visual design met Airen's goal. Do not treat “no overflow,” passing tests, smaller cards or correct focus as visual approval.

Fresh landing captures at 1440, 1024 and 390px are alongside this file. The current design still consists of a large flat purple split hero, a small schematic card, a status rail, plain role descriptions and an access/privacy block. The compositions are tidy enough to function but lack the specificity, visual hierarchy and finish requested. The shared indigo/violet identity is accepted; this particular landing composition is not.

Authenticated screens and native screens are not freshly visually verified by this reset. Do not infer from that uncertainty that they are accepted or excluded. The scope remains every web route, every role, and Flutter.

## Direction to execute

Aim for a composed public-safety product with a clear operational identity. Retain the accepted indigo/violet brand and semantic urgency colors. Replace unfinished compositions rather than adjusting the same card's padding again. Choose details within this direction; Airen has delegated those decisions.

### Landing

- Replace the existing hero arrangement. Build an editorial opening with a concise proposition, one clear resident action, separate returning-account/staff access, and a substantial product demonstration integrated into the composition. Do not leave an isolated little card floating beside oversized text in a flat color field.
- The demonstration should make the actual product legible: one sample report, spatial context, an assigned response and a meaningful update. Use faithful product UI and a carefully composed map/schematic, labeled as a demonstration. Avoid toy geometry, fake operational metrics, placeholder photos and gratuitous dashboard widgets.
- Use one intentional display treatment, readable supporting text and disciplined line lengths. Establish typography roles and optical alignment before adding decorative effects. Preserve the current font if it meets the direction; do not substitute a fashionable font as a proxy for design.
- Create a clear visual sequence after the opening: a concrete reporting-to-response demonstration, concise audience access, and a useful closing/footer. The six-dot status rail and plain audience definition list are replaceable; their information must remain accurate. Alternate density and emphasis rather than stacking equally padded text sections.
- Compose the phone view separately: compact navigation, resident action early, a readable cropped/simplified product demonstration with no essential information lost, and concise secondary content. Do not shrink desktop labels or stack every desktop panel.
- Preserve honest emergency guidance, demo labeling, course credits, actual availability and privacy-review status. Present supporting notices coherently without fabricating authority or policy.

### Auth and resident web

Carry the same typography, materials, alignment and icon system into access pages. The oversized purple explanation boxes remain open to replacement; correct form order alone is not the finish line. Resident screens should foreground the report action and status progress, using clear task-specific layouts for home, reporting and detail. Preserve inline validation and all recovery fixes.

### Staff/admin

Use the accepted v11 concept as a visual reference, then design each task: dense incident inbox, composed incident workspace, map-centered coordination, readable analytics, resource management and audit history. Do not apply the same generic card grid to every route. Make urgency, selection, location, time and next permitted action clear. Keep controls compact and operational content calm. Reuse shared typography, status treatments, navigation and component owners.

### Flutter

Translate the identity into native navigation, forms, sheets, evidence and status views. Give the report flow a coherent visual system across all four actual steps. Preserve drafts, account isolation, submission integrity, permissions, safe areas and text scaling. Native completion requires actual device/emulator evidence.

## Working method

Read current product truth, the whole-product ledger and applicable Software Build Guidelines. Use relevant available design skills, including Impeccable, with their actual instructions. Inspect and preserve current uncommitted work. Reconcile older documents that accidentally narrow this request to the dispatcher dashboard or treat old public layouts as binding.

Write down the selected composition, typography roles, color roles, imagery approach and interaction character before editing. Implement the redesigned landing in the real app, inspect desktop and phone renders, and correct obvious weak areas yourself. Then carry the system through every remaining surface; do not stop for repeated milestone permission requests. If a binding rule requires approval, name the exact rule and present the complete reviewable design decision.

Separate visual acceptance from behavioral verification. Continue necessary registration/provisioning and access-control checks, but do not report those fixes as the visual redesign.

## Acceptance

- The landing has a visibly different composition and a convincing product-specific demonstration. Swapping colors or resizing the existing schematic card does not satisfy this brief.
- Every route has a deliberate page hierarchy and a reviewed desktop/phone composition; native uses native patterns. Inventory rows cannot be completed solely by shared CSS inheritance.
- Product truth, role permissions, keyboard access, reduced motion, readable contrast, failure recovery and existing repairs remain intact.
- Evidence includes real before/after application captures, inspected by the implementing agent, and an honest ledger of visual, behavior and test verification. Generated concepts do not count as runtime proof.
- Report what still falls short of this direction rather than marking a screen polished because tests pass. Airen retains final visual acceptance.
- No commit, push, production data mutation or deployment is authorized by this brief.
